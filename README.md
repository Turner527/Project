# AI-аналитик для стратегического менеджмента банка

Руководитель спрашивает: *«Почему мы отстаём по цели роста розничного кредитования и что делать?»* Агент находит причины
отклонения в данных, проверяет связанные цели и KPI и выдаёт короткую записку: **диагноз**, **2–3 сценария с оценкой
эффекта**, **что проверить вручную** и **ссылки на вызовы инструментов**, из которых взяты цифры.

> **Главный принцип: все числа считает код, а не модель.** GigaChat выбирает, какие инструменты вызвать, и пишет текст по
> их результатам. Детерминированный верификатор проверяет каждое число в ответе по результатам инструментов; ответ с
> числами «из головы» помечается как **«есть непроверенные числа»**, а сами числа подсвечиваются в интерфейсе.

```
вопрос ─► агент (до 6 шагов) ─► адаптер ─► MCP-сервер ─► функции над kpi.xlsx (pandas)
            │  GigaChat выбирает функции         └ либо прямой вызов (тесты, офлайн)
            ▼
   второй вызов модели: JSON по схеме (+1 ретрай) ─► верификатор чисел ─► ответ + журнал SQLite
```

## 1. Установка

Нужен **Python 3.11**.

```bash
python3.11 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Версии `gigachat` (0.2.x) и `mcp` (2.x) ограничены в `requirements.txt`: интерфейсы этих пакетов менялись между мажорными
версиями, код написан под указанные диапазоны.

## 2. Быстрый старт без ключа

Без ключа GigaChat приложение работает в **офлайн-режиме** на заглушке `ScriptedLLM`: она идёт тем же путём, что и модель
(найти KPI → `diagnose_deviation` → собрать записку), но числа берёт дословно из результатов инструментов. Это удобно для
знакомства, демо без сети и тестов. Заглушка — не модель: качество GigaChat она не показывает (см. [§14](#14-что-проверено-а-что-нет)).

```bash
python -m app.main                  # Windows PowerShell: $env:LLM_BACKEND="stub"; python -m app.main
```

Откройте http://127.0.0.1:8000. Если ключ не задан, режим выбирается автоматически; в шапке видна пометка
**«офлайн-заглушка»**. Принудительно: `LLM_BACKEND=stub`.

## 3. Получение ключа в личном кабинете GigaChat API

Названия пунктов кабинета меняются, ориентируйтесь на смысл.

1. Войдите на <https://developers.sber.ru> (через Сбер ID).
2. В **Studio** создайте проект **GigaChat API**.
3. Откройте **«Настройки API»** → **«Получить ключ»**. Скопируйте **«Ключ авторизации»** (Authorization Key, строка в Base64).
   Он показывается один раз; при потере ключ перевыпускают. `Client ID` и `Client Secret` по отдельности не нужны.
4. Запомните **scope**: `GIGACHAT_API_PERS` — для физлиц; `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP` — для юрлиц.
5. Лимит токенов зависит от тарифа, смотрите в кабинете. Один вопрос к агенту — это 3–4 обращения к модели; фактический расход токенов виден в блоке «Как получен ответ» и в сводке пилота (заглушка считает токены приблизительно, по длине текста).

## 4. Сертификат Минцифры

API GigaChat использует сертификат, выпущенный Национальным удостоверяющим центром Минцифры; в системных хранилищах и в
`certifi` его обычно нет, поэтому проверка SSL без него падает. Проверку **отключать нельзя**: проект откажется работать
(`GIGACHAT_VERIFY_SSL_CERTS=false` вызывает ошибку), а в коде нет ни одного обхода.

1. Скачайте **корневой сертификат НУЦ Минцифры** со страницы Госуслуг <https://www.gosuslugi.ru/crt>.
   *(Прямые ссылки на файлы со временем меняются, поэтому здесь дана страница-источник.)*
2. Создайте папку и положите файл в формате PEM:
   ```bash
   mkdir certs
   # файл .crt/.pem из Госуслуг кладём как certs/russian_trusted_root_ca.pem
   ```
3. Если у вас `.cer` в формате DER (двоичный), конвертируйте:
   ```bash
   openssl x509 -inform DER -in russian_trusted_root_ca.cer -out certs/russian_trusted_root_ca.pem
   ```
4. Если и с корневым сертификатом `check_gigachat.py` жалуется на сертификат, добавьте в тот же PEM-файл промежуточный
   («russian_trusted_sub_ca»): просто допишите его PEM-текст в конец файла.

Папка `certs/` и любые `*.pem`, `*.crt`, `*.cer`, `*.key` внесены в `.gitignore`: сертификаты и ключи в git не попадают.

## 5. Создание .env

```bash
cp .env.example .env               # Windows: copy .env.example .env
```

| Переменная | Значение |
|---|---|
| `GIGACHAT_CREDENTIALS` | ключ авторизации из шага 3 |
| `GIGACHAT_SCOPE` | `GIGACHAT_API_PERS` (по умолчанию), `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP` |
| `GIGACHAT_CA_BUNDLE` | путь к PEM из шага 4, например `certs/russian_trusted_root_ca.pem` (относительный — от корня проекта) |
| `GIGACHAT_MODEL` | модель с вызовом функций; по умолчанию `GigaChat-2-Pro` (для более сложных вопросов можно `GigaChat-2-Max`) |
| `LLM_BACKEND` | `gigachat` / `stub` / `auto` (по умолчанию: GigaChat, если задан ключ, иначе заглушка) |
| `TOOLS_BACKEND` | `mcp` (по умолчанию: инструменты в отдельном MCP-процессе) или `direct` (те же функции напрямую) |
| `LOG_DB_PATH` | путь к SQLite-журналу, по умолчанию `logs/pilot.db` |
| `PORT` | порт сервера, по умолчанию 8000 |

## 6. Проверка связи с GigaChat

```bash
python check_gigachat.py            # полная проверка
python check_gigachat.py --offline  # только настройки и сертификат
```

Скрипт идёт по цепочке «настройки → сеть → TLS с вашим сертификатом → ключ → модель → тестовый запрос → вызов функций»
и на каждом сбое говорит, **что именно** не так и что делать. Зависимые шаги при ошибке пропускаются.

| Симптом в выводе | Причина | Что делать |
|---|---|---|
| `Ключ авторизации — GIGACHAT_CREDENTIALS не задан` / `Ключ авторизации отклонён (401)` | ключ | перевыпустить ключ, вставить «Ключ авторизации» целиком, без кавычек |
| `Неверный scope` / `Доступ запрещён (403)` | scope не подходит к типу аккаунта | выбрать `PERS`, `B2B` или `CORP` по аккаунту |
| `Сертификат Минцифры — файл не найден / не удалось прочитать как PEM` | сертификат | шаг 4 |
| `TLS: сертификат сервера не прошёл проверку` | сертификат | указать корневой сертификат, при необходимости добавить промежуточный |
| `Сеть: … имя хоста не найдено` / `превышено время ожидания` | сеть | интернет, DNS, файрвол (порт 9443), прокси |
| `Превышен лимит запросов (429)` / `Закончился пакет токенов (402)` | лимиты | подождать или пополнить пакет в кабинете |
| `Модель … нет в списке доступных` | неверный `GIGACHAT_MODEL` | взять название из списка в сообщении |
| `Вызов функций — модель ответила текстом` | слабая модель | `GigaChat-2-Pro` или `GigaChat-2-Max` |

Если в окружении задан прокси (`HTTPS_PROXY`), прямые TCP/TLS-тесты пропускаются (они идут мимо прокси и дали бы ложную
ошибку), а связь проверяет шаг авторизации через SDK.

## 7. Данные

В репозитории уже лежат готовые `data/kpi.xlsx` и `data/anomalies.json`. Перегенерировать (результат детерминирован):

```bash

```

Витрина синтетическая, реальные данные не использовались: 18 KPI, 8 целей в иерархии, 5 сегментов клиентов
(Массовый, Зарплатные, Премиум, Молодёжь, Самозанятые и ИП), 18 месяцев (2025-04 … 2026-09), сезонность и шум.

**Четыре заложенные аномалии** (описание причин — в `data/anomalies.json`, на нём построены evals):

| № | Что видно в данных | Сегмент | Что объясняет (в данных) |
|---|---|---|---|
| A1 | отставание по выдачам розничных кредитов | Молодёжь | упала доля одобрения заявок |
| A2 | рост просрочки 30+ (побочный эффект ускорения выдач) | Самозанятые и ИП | резко сократилось время решения по кредиту |
| A3 | недобор комиссионного дохода | Премиум | упал оборот по картам |
| A4 | рост оттока клиентов | Зарплатные | падают остатки и число активных клиентов |

### Формат загружаемого xlsx

Кнопка **«Загрузить xlsx»** принимает свою витрину. Три листа и колонки (регистр и лишние пробелы не важны):

| Лист | Колонки |
|---|---|
| `goals` | `цель`, `родительская цель` (у корневой пусто), `владелец`, `KPI`, `единица`, `тип`, `лучше` |
| `facts` | `KPI`, `месяц` (дата или текст `2026-04`), `сегмент`, `план`, `факт` |
| `links` | `KPI-причина`, `KPI-следствие`, `влияние` (`положительно` / `отрицательно`) |

* `тип`: **`поток`** (суммируется по месяцам и сегментам: выдачи, доходы), **`остаток`** (значение на конец периода,
  сумма по сегментам: портфель, число клиентов), **`доля`** (простое среднее по месяцам и сегментам: проценты, NPS).
* `лучше`: **`больше`** или **`меньше`**. Без этого нельзя понять, плохо ли превышение плана (для просрочки — плохо).
* Каждый KPI встречается на листе `goals` один раз; **первый KPI цели считается главным**.

Проверяются листы, колонки, пустые ячейки, типы (числа текстом не принимаются), распознавание месяцев, допустимые значения,
ссылки между листами, дубли и циклы в иерархии целей. Все найденные проблемы показываются сразу и по-русски, с номерами
строк, например: `Лист «facts», колонка «факт»: пустые ячейки в строках 5, 9, 13 (всего 3).` Принятый файл сохраняется как
`data/uploads/active.xlsx` и остаётся активным после перезапуска; **вернуться к демо-данным** — удалить этот файл.

## 10. Evals

```bash
python -m evals.run_evals                       # настоящая модель, если задан ключ
python -m evals.run_evals --backend stub        # конвейер без модели
python -m evals.run_evals --limit 8 --note "правка про сценарии"
python -m evals.build_questions                 # пересобрать вопросы из anomalies.json
```

36 вопросов (`evals/questions.json`): по 8 формулировок на каждую из четырёх аномалий (вопрос про цель, про KPI, про
сегмент, про связанные показатели, «записка для правления», «что если вернуть сегмент к плану», окно «три месяца»,
разговорная формулировка) и 4 контрольных вопроса про KPI **без** аномалии. Три метрики:

| Метрика | Как считается |
|---|---|
| **Причина названа верно** | в `key_segments` или в причине назван нужный сегмент; где вопрос про причину — ещё и нужный KPI-драйвер (названия сравниваются по основам слов, допускается «одобрение заявок»). Для контрольных KPI верно — не называть проблемных сегментов |
| **Числа совпадают с витриной** | все эталонные числа вопроса есть в ответе с допуском на округление записи (эталон посчитан генератором независимо от инструментов) |
| **Доля ответов с непроверенными числами** | доля ответов, где верификатор нашёл числа без источника в результатах инструментов |

Каждый прогон добавляет строку в **`evals/results.csv`** (дата, версия промпта, модель, три метрики, пометка) и сохраняет
разбор по каждому вопросу в `evals/details/*.json`. В конце печатается сравнение с предыдущим прогоном **той же модели** —
так видно эффект правки. Версия промпта — хеш его текста (`v1-704e58`), поэтому любая правка текста автоматически
получает новую версию.

```
Прогон … · промпт v1-704e58 · stub · инструменты: mcp · вопросов: 36 (ошибок: 0)
  причина названа верно               100.0%   Δ +13.9 п.п. к прогону … (промпт v1-17c636)
  числа совпадают с витриной          100.0%   Δ +2.8 п.п. к прогону … (промпт v1-17c636)
  ответы с непроверенными числами       0.0%   Δ +0.0 п.п. к прогону …
```

> **Как читать результат.** 100% на заглушке — это проверка согласованности инструментов, верификатора и эталонов, а не
> оценка качества GigaChat. Именно так первые прогоны нашли три реальные проблемы (поиск KPI терялся на длинных вопросах;
> в промпте не было различия «причина / следствие» и правила «тот же сегмент»; эталон не учитывал несколько драйверов) —
> они исправлены и закреплены тестами. Реальную оценку даёт только прогон с вашим ключом.

## 11. Сводка для пилота

```bash
python -m logs.pilot_summary [--db путь] [--top 5]
```

Выводит: число запросов, долю ответов со статусом «проверен», долю оценок «полезно» (и охват оценками), самые частые
вопросы, число повторных пользователей, среднюю задержку и расход токенов. В SQLite (`logs/pilot.db`) для каждого запроса
хранятся время, вопрос, вызовы инструментов с аргументами и результатами, итоговый ответ, статус верификации, задержка,
токены, оценка, комментарий, версия промпта и модель.

*Повторный пользователь* — клиент (идентификатор хранится в браузере), у которого 2 и более запросов; отдельно показано,
сколько из них вернулись в другой день. Журнал содержит тексты вопросов, поэтому он не попадает в git и должен храниться
по правилам, принятым для рабочих данных пилота.

## 12. Структура проекта

```
data/        generate.py (генератор), validation.py (проверка xlsx), schema.py, kpi.xlsx, anomalies.json
tools/       core.py (6 инструментов), mcp_server.py (MCP-сервер), datastore.py (активная витрина)
agent/       llm.py (интерфейс LLMClient + GigaChat), tool_adapter.py (MCP → functions), loop.py (цикл агента),
             schemas.py (Pydantic-схема записки), prompts.py, verifier.py, stub_llm.py (офлайн-заглушка)
app/         main.py (FastAPI), static/index.html (интерфейс)
evals/       build_questions.py, questions.json, scoring.py, run_evals.py
logs/        store.py (SQLite-журнал), pilot_summary.py
tests/       188 тестов
check_gigachat.py · .env.example · requirements.txt · .gitignore
```

Инструменты (`tools/core.py`), каждый возвращает JSON с числами и `call_id`; целые таблицы не отдаются:
`find_kpis_by_goal`, `get_deviation`, `break_down_by_segment`, `get_related_kpis`, `get_goal_info` и составной
`diagnose_deviation` (отклонение + с какого месяца держится + разбивка по сегментам + связанные KPI + арифметика сценариев).

## 13. Принятые решения и допущения

Неясные места решены разумным вариантом, чтобы не останавливаться на вопросах. Всё ниже можно изменить.

**Данные и расчёты**
* К листу `goals` добавлены три обязательные колонки (`единица`, `тип`, `лучше`): без них нельзя корректно агрегировать
  показатели и понять, что считать отставанием.
* Для относительных показателей итог по сегментам — **простое среднее без весов**. Для продакшена нужны веса (например,
  портфель). Вклад сегмента = его отклонение / сумма отклонений сегментов, поэтому может быть больше 100% или отрицательным.
* Отклонение **значимо от 3%** от плана (`SIGNIFICANT_PCT`). Без указанного периода берутся последние 6 месяцев; фраза «за последние N месяцев»
  передаётся параметром `last_months`.
* **Оценка эффекта сценариев — арифметика, а не прогноз:** «что будет, если сегмент вернётся к плану» (100%, 50%, при
  значимом втором сегменте — два сегмента). В таблице `links` нет коэффициентов влияния, поэтому побочные эффекты на другие
  KPI оцениваются только качественно (направление связи), и в допущениях ответа это сказано прямо.

**Модель и промпт**
* Температура `0.01` (а не 0: в некоторых API нулевое значение трактуется как «по умолчанию»).
* Структурированный вывод — через промпт, Pydantic-валидацию и **один** ретрай с текстом ошибки, без `response_format`
  (так код не зависит от поддержки схем конкретной версией API). Итоговый вызов идёт с `function_call="none"`.
* По умолчанию модель `GigaChat-2-Pro`. Версия промпта — хеш текста.
* Причиной считается подтверждённый связанный KPI с отношением «влияет на выбранный» **в том же сегменте**; KPI «зависит от
  выбранного» названы последствиями. Это правило найдено evals и записано в системный промпт.

**Верификатор** сверяет числа ответа с числовыми полями результатов инструментов (и с числами из вопроса) по модулю, с
допуском на округление так, как число записано (`86,7` → ±0,05; `87` → ±0,5). Не считаются числами даты, годы, `call_id`,
метки вида `S1` и `30+`, а также целые до 12 без единицы измерения («3 сценария», «6 мес.»).

**Прочее:** инструменты по умолчанию работают в отдельном MCP-процессе (stdio), прямой режим — для тестов и офлайна; ключи
не передаются в процесс инструментов; загруженный xlsx переживает перезапуск; при `LLM_BACKEND=auto` без ключа включается
заглушка с заметной пометкой в интерфейсе.

## 14. Что проверено, а что нет

**Проверено автоматически** (188 тестов + ручные прогоны): расчёты против независимого эталона; MCP-сервер и адаптер
(включая реальный подпроцесс); цикл агента, ретрай и лимит шагов; верификатор; валидация xlsx; API; интерфейс пройден в
Chromium (вопрос → ответ → трасса → оценка с комментарием → ошибка загрузки); диагностика `check_gigachat.py` на пустых и
битых настройках и в сети без выхода наружу.

**Не проверено — обязательно сделайте у себя:**
* **Работа с живым GigaChat.** Ключа у разработчика не было, а хосты Сбера из среды разработки недоступны. Формат запросов
  и разбор ответов проверены моделями самого SDK и подменой клиента, но поведение настоящей модели (выбор функций, строгость
  JSON, качество формулировок) и реакция API на параметры `function_call="none"` и `max_tokens` — нет. Первым делом выполните `python check_gigachat.py`, затем `python -m evals.run_evals` и
  посмотрите, какие вопросы не прошли; вероятно, потребуется правка промпта (метрики покажут её эффект).
* **Ссылки на сертификат Минцифры** не проверялись (доступ из среды разработки закрыт); дана страница Госуслуг.
* **Нет оценки качества модели:** 100% на заглушке не говорит о качестве GigaChat.

**Ограничения:** верификатор подтверждает, что число *есть* в результатах, но не что оно относится к названному в тексте
показателю; причины вне данных (решения, акции, поведение клиентов) агент не знает и выносит их в «что проверить
вручную»; синтетические данные проще реальных.

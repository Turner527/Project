# PRISMA — анализ отчётов и KPI

Загрузите любой отчёт из Excel или CSV — продажи, маркетинг, поддержку, сеть отделений, банковские KPI. **GigaChat
прочитает сводку отчёта, порекомендует, как построить дашборд, и напишет инсайты; программа построит дашборд по его
рекомендациям.** После этого можно спрашивать, **что в отчёте изменилось и почему**, и обсуждать стратегические вопросы.
Агент находит, где именно произошло изменение (канал, отдел, регион, продукт), проверяет связанные показатели и выдаёт
короткую записку: **диагноз**, **2–3 сценария с оценкой эффекта**, **что проверить вручную** и **ссылки на вызовы
инструментов**, из которых взяты цифры. Изначальный сценарий проекта — *«Почему мы отстаём по цели роста розничного
кредитования и что делать?»* на витрине KPI банка — остаётся рабочим частным случаем.

> **Главный принцип: все числа считает код, а не модель.** GigaChat выбирает, какие инструменты вызвать и какие блоки
> показать на дашборде, и пишет текст по результатам расчётов. Детерминированный верификатор проверяет каждое число в
> ответе и в инсайтах по результатам расчётов; текст с числами «из головы» помечается как **«есть непроверенные числа»**,
> а сами числа подсвечиваются в интерфейсе.

```
отчёт xlsx / csv ─► профилировщик находит роли столбцов ─► вы проверяете и правите ─► таблица + спецификация
таблица ─► сводка без строк ─► GigaChat: блоки и инсайты (JSON) ─► код сверяет план, строит блоки, проверяет числа ─► дашборд
вопрос (по данным или стратегический) ─► агент (до 6 шагов; видит выводы дашборда) ─► адаптер ─► MCP-сервер ─► расчёты над таблицей (pandas)
            │  GigaChat выбирает функции         └ либо прямой вызов (тесты, офлайн)
            ▼
   второй вызов модели: JSON по схеме (+1 ретрай) ─► верификатор чисел ─► ответ + журнал SQLite
```

## 1. Установка

Нужен **Python 3.11**.

```bash
python3.11 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Версии `gigachat` (0.2.x) и `mcp` (2.x) ограничены в `requirements.txt`: интерфейсы этих пакетов менялись между мажорными
версиями, код написан под указанные диапазоны.

## 2. Быстрый старт без ключа

Без ключа GigaChat приложение работает в **офлайн-режиме** на заглушке `ScriptedLLM`: она идёт тем же путём, что и модель
(найти показатель → `diagnose_change` → собрать записку), но числа берёт дословно из результатов инструментов. Это удобно
для знакомства, демо без сети и тестов. Заглушка — не модель: качество GigaChat она не показывает (см. [§16](#16-что-проверено-а-что-нет)).

```bash
python -m app.main                  # Windows PowerShell: $env:LLM_BACKEND="stub"; python -m app.main
```

Откройте http://127.0.0.1:8000. Если ключ не задан, режим выбирается автоматически; в шапке видна пометка
**«офлайн-заглушка»**. Принудительно: `LLM_BACKEND=stub`. Чтобы сразу попробовать свой отчёт, нажмите **«Загрузить отчёт»**
и выберите любой файл из `data/samples/` (см. [§7](#7-свои-отчёты-и-данные)), затем **«Построить дашборд»** (см. [§8](#8-дашборд-по-отчёту)).

## 3. Получение ключа в личном кабинете GigaChat API

Названия пунктов кабинета меняются, ориентируйтесь на смысл.

1. Войдите на <https://developers.sber.ru> (через Сбер ID).
2. В **Studio** создайте проект **GigaChat API**.
3. Откройте **«Настройки API»** → **«Получить ключ»**. Скопируйте **«Ключ авторизации»** (Authorization Key, строка в Base64).
   Он показывается один раз; при потере ключ перевыпускают. `Client ID` и `Client Secret` по отдельности не нужны.
4. Запомните **scope**: `GIGACHAT_API_PERS` — для физлиц; `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP` — для юрлиц.
5. Лимит токенов зависит от тарифа, смотрите в кабинете. Один вопрос к агенту — это 3–4 обращения к модели; фактический расход токенов виден в блоке «Как получен ответ» и в сводке пилота (заглушка считает токены приблизительно, по длине текста).

## 4. Сертификат Минцифры

API GigaChat использует сертификат, выпущенный Национальным удостоверяющим центром Минцифры; в системных хранилищах и в
`certifi` его обычно нет, поэтому проверка SSL без него падает. Проверку **отключать нельзя**: проект откажется работать
(`GIGACHAT_VERIFY_SSL_CERTS=false` вызывает ошибку), а в коде нет ни одного обхода.

1. Скачайте **корневой сертификат НУЦ Минцифры** со страницы Госуслуг <https://www.gosuslugi.ru/crt>.
   *(Прямые ссылки на файлы со временем меняются, поэтому здесь дана страница-источник.)*
2. Создайте папку и положите файл в формате PEM:
   ```bash
   mkdir certs
   # файл .crt/.pem из Госуслуг кладём как certs/russian_trusted_root_ca.pem
   ```
3. Если у вас `.cer` в формате DER (двоичный), конвертируйте:
   ```bash
   openssl x509 -inform DER -in russian_trusted_root_ca.cer -out certs/russian_trusted_root_ca.pem
   ```
4. Если и с корневым сертификатом `check_gigachat.py` жалуется на сертификат, добавьте в тот же PEM-файл промежуточный
   («russian_trusted_sub_ca»): просто допишите его PEM-текст в конец файла.

Папка `certs/` и любые `*.pem`, `*.crt`, `*.cer`, `*.key` внесены в `.gitignore`: сертификаты и ключи в git не попадают.

## 5. Создание .env

```bash
cp .env.example .env               # Windows: copy .env.example .env
```

| Переменная | Значение |
|---|---|
| `GIGACHAT_CREDENTIALS` | ключ авторизации из шага 3 |
| `GIGACHAT_SCOPE` | `GIGACHAT_API_PERS` (по умолчанию), `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP` |
| `GIGACHAT_CA_BUNDLE` | путь к PEM из шага 4, например `certs/russian_trusted_root_ca.pem` (относительный — от корня проекта) |
| `GIGACHAT_MODEL` | модель с вызовом функций; по умолчанию `GigaChat-2-Pro` (для более сложных вопросов — `GigaChat-2-Max` или `GigaChat-3-Ultra`). Менять можно и в интерфейсе: «Подключить GigaChat» → «Модель» |
| `LLM_BACKEND` | `gigachat` / `stub` / `auto` (по умолчанию: GigaChat, если задан ключ, иначе заглушка) |
| `TOOLS_BACKEND` | `mcp` (по умолчанию: инструменты в отдельном MCP-процессе) или `direct` (те же функции напрямую) |
| `LOG_DB_PATH` | путь к SQLite-журналу, по умолчанию `logs/pilot.db` |
| `PORT` | порт сервера, по умолчанию 8000 |

**Вариант без правки файлов — через интерфейс.** Запустите сервер, нажмите в шапке **«Подключить GigaChat»**, вставьте
ключ авторизации, выберите scope и приложите сертификат Минцифры (PEM). Ключ проверяется живым запросом к GigaChat
и **только при успехе** сохраняется в `.env` (права 600), сертификат — в `certs/`; модель переключается без перезапуска.
Подключение из интерфейса принимается только с локального адреса (`127.0.0.1`). Если сервер открыт по сети, эту
форму нужно закрыть паролем или отключить.

## 6. Проверка связи с GigaChat

```bash
python check_gigachat.py            # полная проверка
python check_gigachat.py --offline  # только настройки и сертификат
```

Скрипт идёт по цепочке «настройки → сеть → TLS с вашим сертификатом → ключ → модель → тестовый запрос → вызов функций →
план дашборда» и на каждом сбое говорит, **что именно** не так и что делать. Зависимые шаги при ошибке пропускаются.

| Симптом в выводе | Причина | Что делать |
|---|---|---|
| `Ключ авторизации — GIGACHAT_CREDENTIALS не задан` / `Ключ авторизации отклонён (401)` | ключ | перевыпустить ключ, вставить «Ключ авторизации» целиком, без кавычек |
| `Неверный scope` / `Доступ запрещён (403)` | scope не подходит к типу аккаунта | выбрать `PERS`, `B2B` или `CORP` по аккаунту |
| `Сертификат Минцифры — файл не найден / не удалось прочитать как PEM` | сертификат | шаг 4 |
| `TLS: сертификат сервера не прошёл проверку` | сертификат | указать корневой сертификат, при необходимости добавить промежуточный |
| `Сеть: … имя хоста не найдено` / `превышено время ожидания` | сеть | интернет, DNS, файрвол (порт 9443), прокси |
| `Превышен лимит запросов (429)` / `Закончился пакет токенов (402)` | лимиты | подождать или пополнить пакет в кабинете |
| `Модель … нет в списке доступных` | неверный `GIGACHAT_MODEL` | взять название из списка в сообщении |
| `Вызов функций — модель ответила текстом` | слабая модель | `GigaChat-2-Pro` или `GigaChat-2-Max` |
| `План дашборда — … по умолчанию` | модель не вернула план в нужном формате | смотреть сырой ответ в «Как построен дашборд»; модель посильнее |

Последний шаг строит дашборд по синтетической демо-витрине (около 8 тысяч токенов; ваши данные в проверке не участвуют) и
показывает, вернула ли модель пригодный план и есть ли в её текстах числа без источника.

Если в окружении задан прокси (`HTTPS_PROXY`), прямые TCP/TLS-тесты пропускаются (они идут мимо прокси и дали бы ложную
ошибку), а связь проверяет шаг авторизации через SDK.

## 7. Свои отчёты и данные

### 7.1. Какой файл подойдёт

* **xlsx или csv.** У csv кодировка (UTF-8, Windows-1251) и разделитель (`,` `;` табуляция) определяются сами, числа с
  десятичной запятой и пробелами в разрядах понимаются. Старый `.xls` не читается: сохраните его как `.xlsx` или `.csv`.
* **Одна таблица на листе:** строка заголовков, под ней строки данных; одна строка — сочетание даты и разрезов
  (например, день × канал × кампания). Заголовок отчёта над таблицей и листы вроде «О файле» допускаются.
* **Что нужно:** хотя бы один числовой столбец. Желательны дата (без неё можно сравнивать только с планом), разрезы
  (текстовые столбцы с 2–500 значениями: канал, регион, продукт) и столбец плана. Если сравнивать не с чем (нет ни плана, ни
  прошлых периодов), дашборд показывает значения и структуру, а на вопросы агент отвечает, из чего состоит показатель
  (инструмент `get_structure`), и прямо говорит, что об изменении и его причинах судить нельзя.
* **Что не подойдёт без подготовки:** «широкие» таблицы, где месяцы идут столбцами; объединённые ячейки в таблице;
  план и факт отдельными строками (программа предупредит и подскажет разнести их по столбцам).
* **Размер:** до 15 МБ, до 600 тысяч строк на листе.

### 7.2. Загрузка и проверка ролей столбцов

Кнопка **«Загрузить отчёт»** (или перетаскивание файла) → программа читает файл, **сама определяет роль каждого столбца**
и показывает окно **«Проверьте роли и типы столбцов»**. В нём можно:

* сменить роль столбца: **Дата · Разрез · Показатель · План · Фильтр строк · Не использовать**;
* для показателя — задать название, способ расчёта (**сумма · среднее · на конец периода**), единицу и **что лучше**
  («больше», «меньше», нейтрально): без этого нельзя понять, плохо ли рост расходов или просрочки;
* связать столбец плана с показателем; выбрать значения фильтра;
* включить, отключить, переименовать и **добавить свои отношения** (клики / показы, расходы / лиды и т. п.);
* выбрать другой лист; прочитать предупреждения о качестве данных и заметки из файла.

Что определяется автоматически (это эвристики по названиям и значениям, без модели — поэтому окно проверки обязательно):

| Что | Как определяется |
|---|---|
| **Дата и детализация** | столбец с датами: даты Excel, `2026-09-15`, `15.09.2026`, `2026-09`, «сентябрь 2026», `2026-Q3`; детализация (день, неделя, месяц, квартал, год) — по медианному шагу между датами |
| **Разрез** | текстовый столбец с 2–500 разными значениями; слишком уникальные тексты (комментарии, идентификаторы) пропускаются |
| **Показатель** | числовой столбец; пропускаются идентификаторы (`ID`, `Номер`, подряд идущие целые), календарные признаки (`Год`, `Месяц`) и столбцы с одним значением |
| **Единица** | из названия (`Расходы, руб`, `Время (мин)`), из формата ячейки Excel (₽, %) или столбца валюты — только для денежных столбцов |
| **Доли и проценты** | суммировать их нельзя, поэтому берётся среднее (с предупреждением); значения-доли до 1 показываются в процентах. Точнее задать отношение двух столбцов |
| **Что лучше** | по названию: расходы, затраты, стоимость, время, отток, просрочка, жалобы — «меньше»; обращения, остатки — нейтрально; остальное — «больше» |
| **План** | столбец «План …» привязывается к показателю по общим словам: «План дохода» ↔ «Доход» |
| **Фильтр строк** | служебный признак вида «Период закрыт: Да / Нет»: по умолчанию остаются только «Да», иначе неполный период исказит сравнение |
| **Отношения** | по парам столбцов: CTR, конверсии, стоимость клика / лида / заказа, ROAS, средний чек, выполнение SLA, CSAT, среднее время обработки, конверсия сделок, прибыль и маржа. Считаются как **отношение сумм**, а не среднее готовых процентов |

Проверка при сохранении: названия показателей уникальны, столбцы существуют, даты распознаются (иначе — номера строк
Excel, например `в строках 7, 35, 63`), нечисловые ячейки в показателе (больше 1% — ошибка, меньше — предупреждение),
строки «Итого» исключаются, чтобы суммы не удвоились. Ошибки показываются сразу и по-русски; активный отчёт при этом не
меняется.

**Заметки из файла** (листы «О файле», «Описание», «Справка», строки над таблицей) показываются **только вам** и в модель
**не передаются**: тексты в файлах могут содержать посторонние указания.

### 7.3. Образцы

В `data/samples/` лежат три синтетических отчёта с заложенными аномалиями (реальные данные не используются):

| Файл | Что внутри | Что заложено |
|---|---|---|
| `marketing.xlsx` | 61 день × канал × кампания: расходы, показы, клики, лиды, заказы, выручка | с 15 сентября в канале «Поиск» растут расходы и падает конверсия клик → лид |
| `support.xlsx` | 61 день × очередь × канал: обращения, SLA, оценки, минуты обработки | с 10 сентября в очереди «Техническая поддержка» падают SLA и CSAT, растёт время обработки |
| `branches.xlsx` | 10 месяцев × отделение × продукт: доход, расходы, план дохода, обращения, сделки, «Период закрыт» | в августе–сентябре падает конверсия в «Москва Север» и «Екатеринбург», с августа растут расходы в «Новосибирске»; октябрь не закрыт и отфильтровывается |

Пересоздать (результат детерминирован): `python -m data.generate_samples`.

### 7.4. Стратегическая витрина из трёх листов

Книга, в которой есть как минимум два из листов `goals`, `facts`, `links`, принимается **сразу, без окна проверки**: у такой
витрины есть иерархия целей, владельцы и таблица связей KPI, которых нет в обычной таблице. Колонки (регистр и лишние
пробелы не важны):

| Лист | Колонки |
|---|---|
| `goals` | `цель`, `родительская цель` (у корневой пусто), `владелец`, `KPI`, `единица`, `тип`, `лучше` |
| `facts` | `KPI`, `месяц` (дата или текст `2026-04`), `сегмент`, `план`, `факт` |
| `links` | `KPI-причина`, `KPI-следствие`, `влияние` (`положительно` / `отрицательно`) |

* `тип`: **`поток`** (суммируется по месяцам и сегментам: выдачи, доходы), **`остаток`** (значение на конец периода,
  сумма по сегментам: портфель, число клиентов), **`доля`** (простое среднее по месяцам и сегментам: проценты, NPS).
* `лучше`: **`больше`** или **`меньше`**. Каждый KPI встречается на листе `goals` один раз; **первый KPI цели — главный**.

Проверяются листы, колонки, пустые ячейки, типы, месяцы, допустимые значения, ссылки между листами, дубли и циклы в
иерархии целей; сообщения по-русски, с номерами строк: `Лист «facts», колонка «факт»: пустые ячейки в строках 5, 9, 13
(всего 3).` Внутри эта витрина превращается в ту же таблицу, что и обычный отчёт (разрез «Сегмент», дата «Месяц», план в
каждой строке), и считается тем же движком.

## 8. Дашборд по отчёту

Кнопка **«Построить дашборд»** (на главной, в шапке и в окне «Отчёт принят») запускает цепочку, в которой модель
рекомендует, а код строит и проверяет:

```
отчёт ─► код собирает сводку ─► GigaChat рекомендует блоки и пишет инсайты (JSON) ─► код сверяет план с отчётом
      ─► код строит блоки (числа считает движок) ─► верификатор сверяет числа в текстах ─► дашборд ─► вопросы в чате
```

**Что уходит в GigaChat.** Не строки таблицы, а **сводка** (`tools/dashboard.py`, `build_digest`): до 24 главных
показателей с итогом за период, базой сравнения, изменением и оценкой; ряд из 10 периодов; вклады главных значений
измерений; скрытые ухудшения внутри ровного итога; названия измерений и их первые значения; названия остальных
показателей; у стратегической витрины — цели и связи; до пяти предупреждений о качестве данных (счётчики и номера строк, без
содержимого ячеек). Размер не больше
30 тысяч знаков (около 12 тысяч токенов): у широких отчётов сначала укорачиваются ряды, затем убирается второстепенное.
**Заметки из файла и построчные данные в сводку не попадают.** Точная копия отправленной сводки лежит под дашбордом, в блоке
«Как построен дашборд». Без ключа (`LLM_BACKEND=stub`) наружу не уходит ничего.

**Что возвращает модель** — план в формате JSON (схема `DashboardPlan`): название и краткий вывод; блоки трёх видов
(**kpi** — плитка, **trend** — динамика, **breakdown** — вклады значений измерения); инсайты с важностью (проблема · риск ·
возможность · наблюдение) и ссылками на блоки; что сделать дальше; вопросы для чата. Синонимы (`line` вместо `trend`),
незнакомая важность и слишком длинные тексты прощаются; всё, из чего нельзя построить блок, отвергается с **одним ретраем**
и текстом ошибки схемы.

**Что делает код** (`assemble`):
* названия показателей и измерений сверяются с отчётом без учёта регистра; блоки с несуществующими названиями не строятся,
  дубликаты и блоки сверх лимита (8 плиток, 4 графика динамики, 4 графика вкладов) убираются — каждое такое решение записано в
  «Как построен дашборд»; если блоков получилось меньше трёх, дашборд дополняется блоками по умолчанию;
* **данные блоков считает движок** (`tools/engine.py`, `tools/series.py`) — те же функции и правила, что в ответах чата;
  модель не присылает ни одного числа, которое попало бы в плитку или график;
* числа в текстах плана (заголовок, краткий вывод, подписи, инсайты, шаги, вопросы) сверяются тем же верификатором со сводкой
  и данными блоков: непроверенные подсвечены в тексте и перечислены в шапке дашборда, а такие тексты **не попадают в контекст
  чата**.

**Если модель недоступна или ответила непригодно** (после одного ретрая), показывается **дашборд по умолчанию**: план
собирает код по тем же числам сводки, на странице видны пометка, причина и кнопка «Попробовать ещё раз». Тот же план отдаёт
офлайн-заглушка: это эталонный сценарий для проверки конвейера, а не оценка качества GigaChat.

**Что на дашборде.**
* **Плитки KPI:** значение, изменение к базе (стрелка, процент, слова «хуже плана» / «лучше»), база, цель и владелец, мини-график
  последних периодов (неполные периоды по краям на нём не показываются).
* **Динамика:** укрупнение до 40 точек (дни → недели → месяцы → кварталы → годы); линии по значениям измерения; линия плана;
  красная отметка начала ухудшения; неполные периоды — пунктиром и пустыми точками; подсказка по наведению и по стрелкам
  клавиатуры; линии скрываются кликом по легенде.
* **Вклады:** столбец вправо — значение добавило к изменению, влево — уменьшило; красный — ухудшает показатель, зелёный —
  улучшает; для процентов вклад в процентных пунктах; у отчётов без базы — структура показателя.
* У каждого графика кнопка **«Таблица»** с теми же данными (подсказка никогда не единственный способ прочитать число).
* **Инсайты** со ссылками на блоки (клик прокручивает к блоку), **«что сделать дальше»**, **вопросы одним нажатием**,
  **«Как построен дашборд»** (что отправлено, что вернулось, что изменил код, токены) и оценка «Полезно / Не полезно».

Графики рисует сама страница на SVG, без библиотек и без внешних ресурсов. Цвета рядов — категориальная палитра с
фиксированным порядком, проверенная скриптом `validate_palette.js` на светлой и тёмной карточке; цвет закреплён за значением
измерения, а не за его местом в списке; больше восьми значений — серый цвет «прочие».

**Хранение.** Дашборд сохраняется в `data/uploads/dashboards/<отпечаток>.json` (последние 10; в файле лежит и отправленная
модели сводка, а папка не попадает в git). Отпечаток — хеш
**содержимого** отчёта и ролей столбцов: тот же файл, загруженный заново, находит свой дашборд без нового обращения к
модели; изменился файл или роли — прежнего дашборда нет, а открытый дашборд закрывается. «Построить заново» заменяет сохранённый.

**Вопросы после дашборда.** В системный промпт чата попадает блок «Контекст дашборда» (заголовок, краткий вывод, инсайты с
важностью, шаги), а числа дашборда считаются допустимым источником для верификатора. Вопросы по данным по-прежнему идут через
инструменты. На **стратегические** («что делать в первую очередь?», «какие риски?», «каких данных не хватает?») промпт велит
отвечать так: факты берутся из инструментов или дашборда; предлагаются 2–3 варианта с эффектом **только из результатов
расчёта** (`recovery_scenarios`); названы риски и допущения; всё, что не следует из данных (рынок, решения, поведение
клиентов), помечено гипотезой и вынесено в «что проверить вручную».

**Эндпоинты:** `POST /api/dashboard` (построить и сохранить дашборд активного отчёта; тело необязательно; без модели — 503),
`GET /api/dashboard` (сохранённый дашборд или `null`); краткая карточка есть и в `GET /api/status`.

## 9. Как считаются числа

Все расчёты — в `tools/engine.py`, ни один не делает модель. Правила:

* **Показатель.** `сумма` — сумма по строкам; `среднее` — простое среднее непустых значений; `на конец периода` — значение
  в последнем периоде окна (остатки, число клиентов); **`отношение`** — сумма числителя / сумма знаменателя (CTR = клики /
  показы), умноженная на множитель (100 для процентов). Числитель и знаменатель могут быть выражением `Доход - Расходы`.
* **Окно.** Явный период (`2026-09-15`, `2026-09`, `2026-Q3`), «последние N дней / месяцев» или окно по умолчанию —
  последние 30 дней, 8 недель, 6 месяцев, 4 квартала или 2 года (не больше половины всего ряда). Период обрезается по
  границам данных, об этом сказано в ответе.
* **База сравнения.** `план` (столбец плана), `предыдущий период` той же длины или `тот же период год назад`. По умолчанию
  план, если он есть, иначе предыдущий период. База должна быть покрыта данными минимум на 90%, иначе инструмент
  отвечает, чего не хватает; в записке всегда названо, с чем сравнивали. Строки без плана (или без факта для среднего) в
  сравнении с планом не участвуют.
* **Значимость.** Изменение значимо от **3%** к базе (поле `significant_pct` спецификации). Если оно незначимо, агент так и
  говорит и не ищет причин итога. «Лучше» и «хуже» определяются направлением показателя.
* **Вклад значения измерения** — сколько оно добавило к изменению итога. Для сумм это его собственное изменение. Для
  отношений — разложение **«ставка и структура»**: `w1·(r1 − R0) − w0·(r0 − R0)`, где `w` — доля значения в объёме
  (знаменателе), `r` — его ставка, `R0` — базовое среднее. Сумма вкладов **точно равна** изменению итога, а значение, у
  которого ставка не менялась, а лишь выросла доля в объёме, почти ничего не получает (так конверсия не «обвиняет»
  канал только за то, что в нём выросли клики). Доля вклада в процентах может быть больше 100% или отрицательной, если
  другие значения идут в обратную сторону.
* **Главное измерение.** Перебираются до 6 измерений; главным считается то, где изменение **сильнее всего сосредоточено** в
  немногих значениях: индекс Херфиндаля по вкладам в сторону изменения минус равномерное распределение (46% среди трёх
  значений — почти норма, 44% среди двенадцати — явный всплеск). Если главное значение даёт не менее 40% изменения,
  делается **углубление**: что внутри него по остальным измерениям.
* **С какого времени держится.** Сколько последних интервалов подряд (месяцы, кварталы, недели; для дневных данных —
  семидневки от конца окна) показатель значимо хуже базы, и с какой даты.
* **Локальные отклонения.** Если итог в норме или лучше базы, но отдельное значение измерения ухудшилось на 10% и больше,
  имеет долю в базе не менее 2% и двигает итог не менее чем на 0,5%, оно попадает в `local_deviations` (до трёх). Так
  находятся «ровный итог, но один отдел провалился»; это повод проверить, а не объяснение итога.
* **Связанные показатели.** Числитель и знаменатель отношения, показатели, для которых выбранный служит числителем или
  знаменателем, показатели из таблицы связей и показатели, изменившиеся в то же время (связь у них не установлена).
  Для каждого — в каком значении измерения изменение сильнее всего.
* **Сценарии — арифметика, а не прогноз:** «что будет, если главное значение вернётся к базе» (100%, 50% и, если второе
  значение даёт не меньше 10%, — два значения). Побочные эффекты на другие показатели оцениваются только качественно.

## 12. Evals

```bash
python -m evals.run_evals                       # демо-витрина, настоящая модель, если задан ключ
python -m evals.run_evals --set flat            # плоские отчёты из data/samples (маркетинг, поддержка, отделения)
python -m evals.run_evals --set all --backend stub   # оба набора, конвейер без модели
python -m evals.run_evals --limit 8 --note "правка про сценарии"
python -m evals.build_questions                 # пересобрать вопросы по демо-витрине из anomalies.json
python -m evals.build_flat_questions            # пересобрать вопросы по плоским отчётам
```

**54 вопроса с эталонами.** Демо-витрина (`evals/questions.json`, 36): по 8 формулировок на каждую из четырёх аномалий
(про цель, про KPI, про сегмент, про связанные показатели, «записка для правления», «что если вернуть сегмент к плану»,
окно «три месяца», разговорная) и 4 контрольных вопроса про KPI **без** аномалии. Плоские отчёты
(`evals/questions_flat.json`, 18): маркетинг (расходы, конверсия, стоимость лида, ROAS, «две недели», записка, 2 контрольных),
поддержка (SLA, CSAT, время обработки, «14 дней», разговорная, контрольный), сеть отделений (конверсия за два месяца,
расходы, «ровный итог, но провалилось одно отделение», выполнение плана). Эталоны плоских вопросов считает **независимый
код на pandas** (`evals/build_flat_questions.py`), тесты проверяют, что инструменты с ним совпадают. Три метрики:

| Метрика | Как считается |
|---|---|
| **Причина названа верно** | в `key_segments` или в причине назван нужный сегмент (канал, очередь, отделение); где вопрос про причину — ещё и нужный показатель-драйвер (названия сравниваются по основам слов). Для контрольных вопросов верно — не называть проблемных значений |
| **Числа совпадают с эталоном** | все эталонные числа вопроса есть в ответе с допуском на округление записи |
| **Доля ответов с непроверенными числами** | доля ответов, где верификатор нашёл числа без источника в результатах инструментов |

Каждый прогон добавляет строку в **`evals/results.csv`** (дата, версия промпта, модель, набор данных, три метрики,
пометка) и сохраняет разбор по каждому вопросу в `evals/details/*.json`. В конце печатается сравнение с предыдущим
прогоном **той же модели на тех же данных** — так видно эффект правки. Версия промпта — хеш его текста (`v2-…`), поэтому
любая правка текста автоматически получает новую версию. Для каждого набора поднимается свой процесс инструментов.

```
Прогон … · промпт v2-… · stub · инструменты: mcp · вопросов: 54 (ошибок: 0)
  причина названа верно               100.0%
  числа совпадают с эталоном          100.0%
  ответы с непроверенными числами       0.0%
```

**Evals дашборда** — отдельный прогон, потому что здесь оценивается не ответ на вопрос, а план, который вернула модель:

```bash
python -m evals.run_dashboard_evals                       # демо-витрина и три образца, модель по окружению
python -m evals.run_dashboard_evals --set flat --backend stub --note "правка промпта дашборда"
```

Для каждого набора дашборд строится так же, как в приложении, и оценивается по тому, что заложено в данные:

| Метрика | Как считается |
|---|---|
| **План в нужном формате** | модель вернула разбираемый план (иначе показан дашборд по умолчанию, и все метрики качества плана — ноль) |
| **Предложенные блоки построены** | доля блоков из ответа модели, которые удалось построить по отчёту (остальные — несуществующие показатели и разрезы, дубликаты, лимиты) |
| **Числа в текстах без источника** | доля чисел в заголовке, выводе, инсайтах и шагах, которых нет в сводке и данных блоков |
| **Заложенные причины названы** | доля заложенных причин (четыре сегмента демо-витрины; «Поиск»; «Техническая поддержка»; «Новосибирск», «Москва Север» и «Екатеринбург»), названных в кратком выводе или инсайтах |
| **Есть блоки всех возможных видов** | плитки, динамика и вклады — те, что возможны для отчёта (динамика — при наличии дат, вклады — при наличии разрезов) |

Строка прогона добавляется в `evals/results_dashboard.csv` (дата, версия промпта дашборда `d1-…`, модель, набор, метрики), разбор по
наборам — в `evals/details/dashboards-*.json`, в конце печатается сравнение с предыдущим прогоном той же модели.

> **Как читать результат.** 100% на заглушке — это проверка согласованности инструментов, верификатора и эталонов, а не
> оценка качества GigaChat. Именно так первые прогоны нашли реальные проблемы (поиск показателей терялся на длинных
> вопросах; в промпте не было различия «причина / следствие»; названия вроде «Показы» и «Стоимость» совпадали со
> служебными словами) — они исправлены и закреплены тестами. Реальную оценку даёт только прогон с вашим ключом.

## 13. Сводка для пилота

```bash
python -m logs.pilot_summary [--db путь] [--top 5]
```

Выводит: число запросов, долю ответов со статусом «проверен», долю оценок «полезно» (и охват оценками), самые частые
вопросы, число повторных пользователей, среднюю задержку и расход токенов. Построения дашбордов пишутся в тот же журнал
(запись вида «[дашборд] имя файла», в ней план, проверка, токены) и считаются отдельно: сколько построено, сколько со

не влияют. В SQLite (`logs/pilot.db`) для каждого запроса
хранятся время, вопрос, вызовы инструментов с аргументами и результатами, итоговый ответ, статус верификации, задержка,
токены, оценка, комментарий, версия промпта и модель.

*Повторный пользователь* — клиент (идентификатор хранится в браузере), у которого 2 и более запросов; отдельно показано,
сколько из них вернулись в другой день. Журнал содержит тексты вопросов и названия значений из ваших отчётов, поэтому он
не попадает в git и должен храниться по правилам, принятым для рабочих данных пилота.

## 15. Принятые решения и допущения

Неясные места решены разумным вариантом, чтобы не останавливаться на вопросах. Всё ниже можно изменить.

**Данные и расчёты**
* Роли столбцов определяются эвристиками и **подтверждаются человеком**: ошибка в роли (например, код принят за показатель)
  тихо искажает расчёты, поэтому окно проверки показывается всегда. Спецификация сохраняется как есть и не пересчитывается.
* Отношения (конверсии, стоимости, доли) считаются как **отношение сумм**; простое среднее процентов — запасной вариант
  с предупреждением. У стратегической витрины тип «доля» — по-прежнему простое среднее по сегментам без весов.
* Окна и базы по умолчанию — см. [§9](#9-как-считаются-числа); порог значимости 3% (`significant_pct`, в интерфейсе не
  настраивается); для дневных данных «давность» считается семидневками.
* **Оценка эффекта сценариев — арифметика, а не прогноз:** в таблице нет коэффициентов влияния, поэтому побочные эффекты
  на другие показатели оцениваются только качественно, и в допущениях ответа это сказано прямо.
* Пороги локальных отклонений (10% / 2% / 0,5%) подобраны так, чтобы не срабатывать на контрольных показателях образцов и
  демо-витрины; на ваших данных их, возможно, придётся скорректировать (`tools/engine.py`, константы `LOCAL_*`).

**Модель и промпт**
* Температура `0.01` (а не 0: в некоторых API нулевое значение трактуется как «по умолчанию»).
* Структурированный вывод — через промпт, Pydantic-валидацию и **один** ретрай с текстом ошибки, без `response_format`
  (так код не зависит от поддержки схем конкретной версией API). Итоговый вызов идёт с `function_call="none"`.
* По умолчанию модель `GigaChat-2-Pro`. Версия промпта — хеш текста. В системный промпт добавляется каталог активного отчёта
  (период, показатели, измерения и первые значения), собранный кодом.
* Причиной считается числитель или знаменатель формулы либо подтверждённый связанный показатель «влияет на выбранный» **в
  том же значении измерения**; «зависит от выбранного» и «этот показатель — числитель для …» названы последствиями;
  «изменился в тот же период» — лишь совпадением. Эти правила найдены evals и записаны в системный промпт.

**Верификатор** сверяет числа ответа с числовыми полями результатов инструментов (и с числами из вопроса) по модулю, с
допуском на округление так, как число записано (`86,7` → ±0,05; `87` → ±0,5). Запись с множителем («2,8 млн», «450 тыс.»)
сверяется и как есть, и в пересчёте на единицы. Не считаются числами даты, годы, `call_id`, метки вида `S1` и `30+`, а
также целые до 12 без единицы измерения («3 сценария», «6 мес.»).

**Интерфейс:** исходное ТЗ требовало «без тёмной темы», но заказанные позже референсы в стиле Сбера тёмно-зелёные с
переключателем темы, поэтому по умолчанию тёмная тема, а светлая — по кнопке. Вернуть только светлую тему можно, поменяв
`data-theme="dark"` на `light` в `app/static/index.html` и убрав кнопку `theme-btn`. Шрифты и иконки встроены, внешних
ресурсов нет, интерфейс работает офлайн.

**Какие данные уходят в GigaChat:** вопрос пользователя, системный промпт с каталогом отчёта (названия показателей и
измерений, первые значения измерений, период), описания функций, **результаты инструментов** (агрегированные числа,
названия показателей и значений измерений, у стратегической витрины — цели и владельцы) и, когда вы строите дашборд,
**сводка отчёта** (названия, итоги, ряды по периодам, вклады значений; состав — в [§8](#8-дашборд-по-отчёту)), а после
дашборда в промпт чата добавляются его инсайты. Сам файл и построчные данные не отправляются; заметки из файла не
отправляются; без ключа (`LLM_BACKEND=stub`) наружу не уходит ничего. Если названия в отчёте конфиденциальны, согласуйте это
до пилота. **Решение:** в модель передаётся сводка, а не весь отчёт, — так запрос укладывается в контекст модели, а наружу
уходит минимум; для рекомендаций по дашборду достаточно агрегатов.

**Дашборд**
* **Рекомендует модель, считает код.** Любое число на плитке и графике приходит из движка; числа в текстах модели сверяются
  по сводке и данным блоков. Непроверенное число не прячется: оно подсвечено, и такой текст не попадает в контекст чата.
* **Сбой модели не оставляет пустого экрана:** после одного ретрая показывается дашборд по умолчанию с пометкой и причиной.
* **Строгость там, где строить нечего.** Неизвестный вид блока, пустой список блоков или инсайтов — ошибка схемы (ретрай); а
  незнакомая важность инсайта, синоним вида блока или слишком длинный текст прощаются: один ярлык не должен стоить всего плана.
* **Лимиты:** 8 плиток, 4 графика динамики, 4 графика вкладов, не меньше трёх блоков; в сводке до 24 показателей и 30 тысяч знаков.
* **Отпечаток отчёта — по содержимому**, а не по имени и времени файла: повторная загрузка того же отчёта не стоит нового запроса
  к модели.
* **Неполные периоды** (например, последняя неделя с данными за три дня) на графиках показаны пунктиром, на мини-графиках
  убраны: недосчёт сумм выглядел бы как падение, которого не было.
* **Тексты дашборда по умолчанию** (заглушка и запасной план) собраны кодом дословно из чисел сводки: по одному инсайту на
  причину (показатели с общей причиной, например канал «Поиск», названы внутри, а не повторены тремя инсайтами), до пяти причин;
  плитки — главный показатель каждой причины. На демо-витрине так видны все четыре заложенные проблемы.
* **Сводка — данные, а не инструкции:** это сказано в промпте; заметки из файла в модель не попадают вовсе, а в предупреждениях
  о качестве данных образцы ячеек вырезаются (такая ячейка могла бы содержать посторонний текст).

**Прочее:** инструменты по умолчанию работают в отдельном MCP-процессе (stdio), прямой режим — для тестов и офлайна;
ключи не передаются в процесс инструментов; загруженный отчёт переживает перезапуск; при `LLM_BACKEND=auto` без ключа
включается заглушка с заметной пометкой в интерфейсе; сервер по умолчанию слушает только `127.0.0.1`, а подключение
GigaChat из интерфейса принимается только с локального адреса.

## 16. Что проверено, а что нет

**Проверено автоматически** (602 теста + ручные прогоны): расчёты против независимого эталона (генератор демо-витрины и
pandas по образцам); свойство «сумма вкладов равна изменению итога» на случайных данных для всех видов показателей и баз;
чтение и профилирование xlsx/csv; MCP-сервер и адаптер (включая реальный подпроцесс); цикл агента, ретрай и лимит шагов;
верификатор; API загрузки; диагностика `check_gigachat.py` на пустых и битых настройках. **Интерфейс пройден в Chromium**
на экранах 1440 и 390 px, в тёмной и светлой темах: загрузка xlsx и csv → окно проверки ролей (смена роли, отключение
отношения, своё отношение, переключение листа, ошибка сохранения) → вопрос → ответ с плитками → «Как получен ответ» →
оценка → возврат к демо. **Дашборд пройден в Chromium** на экранах 1360, 1024, 900 и 390 px, в тёмной и светлой темах, на
образцах и демо-витрине: построение, открытие сохранённого, перестроение (прежний кадр остаётся), дашборд по умолчанию,
непроверенные числа, ошибки (нет ключа, нет связи, сбой сборки), смена отчёта при открытом дашборде, подсказки графиков,
таблицы вместо графиков, вопрос из дашборда с ответом под ним.

**Проверено на трёх файлах, присланных заказчиком** (`PRISM_marketing`, `PRISM_support`, `PRISM_demo`; образцы в
`data/samples/` построены по их структуре): после правок роли столбцов определились верно (включая «Период закрыт» как
фильтр и пару «План дохода» ↔ «Доход»); расчёты нашли все описанные в файлах сигналы — канал «Поиск», очередь
«Техническая поддержка», отделения «Москва Север» и «Екатеринбург», расходы «Новосибирска». Эти прогоны выявили три
ошибки: вклад в отношение приписывал причину значениям, у которых изменилась только доля в объёме; расходы-«счётчики»
принимались за идентификаторы; валютный знак ставился на столбцы-количества. Все исправлены и закреплены тестами.
Сами файлы заказчика в репозиторий не входят.

**Не проверено — обязательно сделайте у себя:**
* **Дашборд на живом GigaChat** (`python -m evals.run_dashboard_evals` покажет, насколько план пригоден). Проверены разбор и ремонт плана, дашборд по умолчанию и все пути ошибок на подставной
  модели и на заглушке, но не то, как настоящая модель следует формату плана (после одного ретрая вы увидите дашборд по
  умолчанию с пометкой), какие блоки и инсайты она предлагает на ваших отчётах и сколько секунд занимает ответ (ожидается
  10–40). Откройте «Как построен дашборд»: там сводка, сырой ответ при сбое и замечания к плану.
* **Работа с живым GigaChat.** Ключа у разработчика не было, а хосты Сбера из среды разработки недоступны. Формат запросов
  и разбор ответов проверены моделями самого SDK и подменой клиента, но поведение настоящей модели (выбор функций, строгость
  JSON, качество формулировок, умение писать числа ровно так, как в результатах) и реакция API на параметры
  `function_call="none"` и `max_tokens` — нет. Первым делом выполните `python check_gigachat.py`, затем
  `python -m evals.run_evals --set all` и посмотрите, какие вопросы не прошли; вероятно, потребуется правка промпта
  (метрики покажут её эффект).
* **Ссылки на сертификат Минцифры** не проверялись (доступ из среды разработки закрыт); дана страница Госуслуг.
* **Реальные «грязные» отчёты.** Профилировщик проверен на образцах, трёх файлах заказчика и десятках искусственных
  случаев (заголовки над таблицей, csv в Windows-1251, пустые и итоговые строки, нечисловые ячейки), но не на разнообразии
  файлов из разных систем. Объединённые ячейки, сводные таблицы и «широкие» отчёты не поддерживаются.
* **Нет оценки качества модели:** 100% на заглушке не говорит о качестве GigaChat.

**Ограничения:** сводка для дашборда ужимается до 30 тысяч знаков, поэтому у отчётов с сотнями показателей модель видит
только главные (остальные названы списком); верификатор подтверждает, что число *есть* в результатах, но не что оно относится к названному в тексте
показателю; причины вне данных (решения, акции, поведение клиентов) агент не знает и выносит их в «что проверить
вручную»; вклад в отношение объясняет *где* изменилась ставка, но не *почему*; сезонность не вычитается (для этого есть
база «год назад»); синтетические данные проще реальных.

## 17. Что показывать на демо за 15 минут

**Подготовка (до встречи, 5 минут).** `python check_gigachat.py` — все пункты `[OK]`; `python -m app.main`; открыть
страницу; убедиться, что в шапке имя модели, а не «офлайн-заглушка», и «Демо-данные: 18 KPI». Файлы `data/samples/marketing.xlsx`
и `data/samples/branches.xlsx` под рукой. Если загружали что-то раньше — нажать «Вернуться к демо-данным».

| Время | Что делаем | Что говорим |
|---|---|---|
| **0:00–1:00** | Показать страницу и шапку. | Загрузите любой отчёт: GigaChat прочитает его сводку, порекомендует дашборд и инсайты, потом можно задавать вопросы. Принцип: **числа считает код, модель выбирает блоки и пишет текст**; любое число проверяется. |
| **1:00–3:00** | Нажать **«Загрузить отчёт»** → `marketing.xlsx`. В окне «Проверьте роли и типы столбцов» показать: дата, два разреза и показатели найдены сами, единицы и «что лучше» проставлены, предложены отношения (CTR, конверсии, стоимость лида, ROAS). Поменять одну роль, нажать **«Сохранить и анализировать»**. | Программа не знает вашего отчёта заранее — она **предлагает роли, вы подтверждаете**: от этого зависят все расчёты. Показать шапку (бейджи «рекомендации GigaChat» и «числа проверены»), плитки, график динамики по каналам (подсказка при наведении, красная отметка начала ухудшения), столбцы вкладов, инсайты со ссылками на блоки, кнопку **«Таблица»**.
